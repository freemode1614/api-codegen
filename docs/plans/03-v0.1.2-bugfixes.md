## 1. 本地 spec 文件实际不可用 (#1)

### 现象

README 与 CLI/Vite 插件都说 spec 支持「本地路径或 URL」，但 CLI 总是把本地路径拼成
`file://...`，而 `Base.fetchDoc` 走的是 `undici.request`，对 `file://` 直接抛
`Invalid URL protocol: the URL must start with http: or https:`。

### 现状（已部分修复）

- `Base.fetchDoc` 已经能识别 `file://` 与绝对路径（参见 `src/core/base/Base.ts:177-247`）。
- `e2e-local-file.test.ts` 已经覆盖编程式 `codeGen({ docURL })` 调用。
- 但 **CLI** (`src/cli.ts:60-74`) 与 **Vite 插件** (`src/vite-plugin/index.ts:107-114`) 仍会
  把绝对路径包成 `file://` 后直接传给 `codeGen`，而 `codeGen` 调用的 `Base.fetchDoc` 又是
  走 `undici` 分支——**bug 仍在**：CLI/Vite 走的是「包装成 file://」+「Base.fetchDoc 走
  undici」这条不一致的路径。

### 根因

`Base.fetchDoc` 中虽然有 file 分支，但 `Provider` / `codeGen` 文档没有说明调用前是否要
预先剥离 `file://`。CLI/Vite 各自做路径转换，但都没用 `Base.fetchDoc` 的本地分支能力——
更糟的是 `resolveDocURL` (cli.ts) 把「非 http 非绝对」都拼成绝对路径后再次被当成 http
路径走 undici。

### 修复策略

1. **统一路径解析入口**：新增 `Base.resolveSpecURL(input)` 返回 `{ transport, source }`，
   - `transport: 'file' | 'http'`
   - `source: string` —— file 时是绝对路径，http 时是完整 URL

2. **`Base.fetchDoc` 改成接收已解析好的路径/URL**，并依赖上层已经分类好；不要在
   `fetchDoc` 里再做协议识别（避免和 CLI 二次包装冲突）。

3. **CLI** (`src/cli.ts`)：
   - 用 `Base.resolveSpecURL` 分类后**直接传 source** 给 `codeGen`，不再做 `file://` 包装。
   - watch 模式同样用解析后的 file 路径触发。

4. **Vite 插件** (`src/vite-plugin/index.ts`)：同样切换到 `Base.resolveSpecURL`，
   删掉自己的 `if (!docURL.startsWith('http'))` 分支。

5. **`codeGen`** (`src/openapi/index.ts`)：当 transport === 'file' 时直接 `readFile`+`JSON.parse`，
   跳过 `fetchDoc`；这是新的「编程式 API 也能用本地路径」的关键——也是 bug 报告里
   提到的「只有编程式 API 能处理本地文档」的修法（虽然编程式 API 实际能用是因为
   `Base.fetchDoc` 已经修过，但需要把这条路径打通）。

### 验收

- `apicodegen ./docs/openapi.json -o out.ts` 能成功生成（不抛 `Invalid URL protocol`）。
- `apiCodeGenPlugin([{ name, spec: './x.json' }])` 也能成功生成（不抛错，且 `codeGen`
  入参的 `docURL` 是绝对路径而不是 `file://...`）。
- 老的 `codeGen({ docURL: 'file:///abs/path.json' })` 仍然可用（向后兼容）。
- 远程 URL 完全走 undici 分支。

## 2. 完整 petstore3 spec 生成失败 (#2)

### 现象

3.1 petstore 的 `updatePet` 端点使用 `application/x-www-form-urlencoded`，
生成函数名变成 `...UsingPutX-www-form-urlencoded`（实际是
`...UsingPutXWwwFormUrlencoded` 或类似，但仍是非法 / 极丑），prettier 报错
`(` expected，整个 spec 生成挂掉。

### 根因

`src/core/generator/index.ts:832-846` 中，当一个 operation 有多个 request body
media type 时，按 `req.type.split('/')[1]` 生成后缀，然后丢给 `Base.camelCase`
+ `Base.normalize`。对 `application/x-www-form-urlencoded`：

```
normalize('x-www-form-urlencoded') = 'x_www_form_urlencoded'
camelCase('x_www_form_urlencoded') = 'xWwwFormUrlencoded'
```

得到 `petUsingPutXWwwFormUrlencoded` —— Identifier 合法但极丑，且上游 prettier 对
极长 / 不规范的标识符可能触发解析问题。最致命的其实是：**petstore 只有一个
request body media type**（只有 form-urlencoded），但代码的判断是
`shouldAddExtraMethodNameSuffix = requestBody.length > 1`，理应不会走分支——
但实测生成失败，说明问题不止是「多 media type」。

更可靠的根因：当前代码生成「无 requestBody schema 的请求」时（如 `delete`）会
补一个 `{ type: MediaTypes.JSON }` 兜底（见 `index.ts:828-830`），这本身没问题。
但 petstore `updatePet` 走的另一条路径：`getRequestBodyByRef` 返回
`[{ type: 'application/x-www-form-urlencoded', schema: {type:'object',properties:{...}} }]`
——到这里都没有问题。然后在 generator 里，对这个 request body 走 `bodyBlock`，
**关键 bug 在 `bodyBlock`** (`index.ts:690-758`)：

- `isFormDataRequest` = true（因为 type 是 `application/x-www-form-urlencoded`）
- 但 `shouldPutParametersOrBodyInFormData` 的判断逻辑：
  - `isRequestBodyBinary` = false
  - `hasBinaryInParameters` = false（无 formData 参数）
  - `isRequestBodyContainsBinary` = false
  - `parametersShouldPutInFormData.length > 0` —— `parametersShouldPutInFormData`
    过滤的是 `p.in === formData || isBinarySchema`，这里也是 false

→ `shouldPutParametersOrBodyInFormData` = false。所以走的是
**JSON.stringify 分支**！而这个 body 不是 JSON，应该是 `URLSearchParams`。

那么真实失败原因 ≠「函数名非法」，而是 **#5 form-urlencoded body 用了 JSON.stringify**。
但 bug 报告里同时提到 `x-www-form-urlencoded` 进入函数名 —— 那是因为如果同一 operation
有多个 media type（实际 petstore 没有），才会触发函数名分叉。

### 修复策略

修复两件事：

1. **多 media type 函数名后缀生成**：新增 `Base.mediaTypeToSuffix(type: string)`：
   - 维护已知映射：`multipart/form-data` → `FormData`，
     `application/json` → `Json`，`application/x-www-form-urlencoded` →
     `FormUrlencoded`，`application/octet-stream` → `OctetStream`，`text/plain`
     → `Text`。
   - 未知类型 fallback 到 `Base.camelCase(Base.normalize(type.split('/')[1]))`。
   - 在 `generator/index.ts:832-846` 改用此函数。

2. **form-urlencoded 也走 form-data 分支**（详见 #5 的修复）。

### 验收

- 用 `api-docs/openapi/3.1/json/petstore.json` 作为输入，能完整生成（不再 prettier 报错）。
- 函数名合理（如 `updatePetUsingPutFormUrlencoded`，而不是 `...XWwwFormUrlencoded`）。

## 3. JSON POST/PUT 缺 Content-Type (#3)

### 现象

生成的 `fetch(url, { method: 'POST', body: JSON.stringify(req) })` 不带
`Content-Type: application/json`，导致真实服务器返回 415。

### 根因

`src/core/client/fetch.ts:54-128` 的 `toLiterlExpression` 只在有 `header` 参数
时才生成 `headers` 字段；对 JSON body 没有任何 Content-Type。

### 修复策略

1. `FetchAdapter` / `AxiosAdapter` 的 `client()` 函数中：
   - 计算 `bodyContentType: string | undefined`：
     - `shouldUseFormData`（即 multipart/form-data）→ undefined（浏览器自动加 boundary）
     - `application/x-www-form-urlencoded` → `'application/x-www-form-urlencoded'`
     - 其它（含 `application/json`、OCTET-STREAM、TEXT 等）→ `requestBody?.type`
       （并 trim 小写）。
     - 没有 request body → undefined。
   - 当 `bodyContentType` 有值时，向 `headers` 注入
     `'Content-Type': bodyContentType`（合并到已有的 header 参数中）。

2. **headers 字段永远存在**：把 `inHeader.length > 0 ?` 改成「只要有 Content-Type 要注入
   或 inHeader 非空」就输出 `headers: { ... }`。

3. 对 **Axios** (`src/core/client/axios.ts`) 同样处理。

### 验收

- 生成的 `POST` JSON body 调用 fetch 时显式带 `headers: { 'Content-Type': 'application/json' }`。
- 生成的 `POST` form-urlencoded 调用带 `Content-Type: application/x-www-form-urlencoded`。
- 生成的 `POST` multipart 不显式设置 Content-Type（保留自动 boundary）。
- 已有 header 参数时，与 Content-Type 合并（重复 key 时 Content-Type 优先）。

## 4. multipart 上传 body 用了 JSON.stringify (#4)

### 现象

`requestBody` 是 `multipart/form-data` + 包含文件字段时，生成的是
`body: JSON.stringify(req)`（req.file 是 Blob），实际上传必挂。

### 根因

`Generator.bodyBlock` (`src/core/generator/index.ts:690-758`) 的
`shouldPutParametersOrBodyInFormData` 判定只在「同时存在 formData 参数或二进制
schema」时才走 `toFormDataStatement` 分支。但 3.x 风格的 multipart 端点通常
**只在 requestBody schema 里有 file/binary 字段**（没有任何 `formData` 参数），
于是被错误地归到 JSON 分支。

### 修复策略

放宽条件：只要 `requestBody?.type === 'multipart/form-data'` **且**
`requestBody?.schema` 包含 binary 字段，就走 `toFormDataStatement`。新条件：

```ts
const isMultipartWithFiles =
  requestBody?.type === 'multipart/form-data' &&
  !!requestBody.schema && (
    (requestBody.schema.type === 'array' && Generator.isBinarySchema(requestBody.schema)) ||
    isRequestBodyContainsBinary
  );

const shouldPutParametersOrBodyInFormData =
  !!isFormDataRequest && (
    isRequestBodyBinary ||
    hasBinaryInParameters ||
    isRequestBodyContainsBinary ||
    parametersShouldPutInFormData.length > 0 ||
    isMultipartWithFiles
  );
```

同时，**`toFormDataStatement`** 也要改：当前它依赖 `parametersShouldPutInFormData`
（formData 参数）来 iterate，如果参数空就只迭代 `requestBody.properties`。
确认这条路径在「纯 3.x multipart body」下也能工作——应已 OK（`if (requestBody &&
requestBody.properties...)` 块已经处理 properties），但需测试覆盖。

### 验收

- 3.x multipart body 含 `type: string, format: binary` 时生成 `const fd = new FormData();
  fd.append('file', req.file); ...`，`body: fd`。
- 与 Swagger 2.0 (`formData` 参数) 路径行为一致。

## 5. form-urlencoded body 用了 JSON.stringify (#5)

### 现象

`application/x-www-form-urlencoded` body 也走 `JSON.stringify` 分支，没用
`URLSearchParams`。

### 修复策略

在 `bodyBlock` / `client()` 中：
1. 当 `requestBody.type === 'application/x-www-form-urlencoded'`：
   - 计算 `shouldUseURLSearchParams = true`
   - 在生成的代码前插入：
     ```ts
     const params = new URLSearchParams();
     for (const key in req) {
       const v = req[key];
       if (v !== undefined && v !== null) params.append(key, String(v));
     }
     ```
     或者更简单：
     ```ts
     const params = new URLSearchParams(req as Record<string, string>);
     ```
     **后者会在 key 是 undefined 时丢失键**，反而顺便解决了 #8 —— 这是一个很好的
     「一处修复两个 bug」机会。
   - `body: params` 而非 `JSON.stringify(req)`。
   - Content-Type = `application/x-www-form-urlencoded`（#3 修复已经覆盖）。
2. 若 schema 字段类型为 `array`/`object`，逐项 `params.append(key, JSON.stringify(v))`。

> 注意：URLSearchParams 的入参会被自动 URL 编码，正合 urlencoded 语义。

### 验收

- 生成函数里出现 `new URLSearchParams(...)`，body 用 `params`。
- Content-Type 注入 `'application/x-www-form-urlencoded'`。

## 6. 忽略 operationId (#6)

### 现象

`Base.pathToFnName` 实际**已经支持** `operationId`（参见 `Base.ts:85-109`），
generator 也传入了 `operationId`（参见 `generator/index.ts:842`）。**实测生成的函数
名是带 `operationId` 的**（`updatePetUsingPut`）。

### 但：vite 插件路径下的 bug 报告描述「全用 pathSegments」

回看 #1 修复：vite 插件自己有一段
```ts
if (!docURL.startsWith('http://') && !docURL.startsWith('https://')) {
  if (docURL.startsWith('/') || docURL.match(/^[A-Za-z]:/)) {
    docURL = `file://${docURL}`;
  } else {
    docURL = path.resolve(process.cwd(), docURL);
  }
}
```
这并没有把 operationId 抹掉。所以 #6 可能是用户「看了 #1 的失败现场下生成的产物」
得到的错觉——生成根本没成功，所以看到的函数名是哪里来的，需要复现确认。

### 修复策略

- **#1 修好后**，#6 应自动消失（因为代码路径本来就尊重 operationId）。
- 仍然加一个测试 `__tests__/naming.test.ts` 增量：覆盖 `Base.pathToFnName` 在
  `operationId = 'addPet'` 之类常见命名下输出正确。
- 增量测试：从 spec 含 `operationId` 的真实生成，确认最终函数名以 operationId 开头。

### 验收

- 生成函数名包含 operationId；如不存在则降级到路径。
- 不再出现 `petFindByStatusUsingGet` 之类的「忽略 operationId」的情况（如果
  spec 里 operationId 是 `findPetsByStatus`）。

## 7. 部分响应无类型 / 数组 body 退化为 unknown (#7)

### 现象

- `petUsingPut` / `petUsingPost` 生成的响应是 `await (await fetch(...)).json()` 没有 `as`
  cast。
- `userCreateWithListUsingPost` 的数组 body 参数类型是 `req: unknown`。

### 根因

1. **响应无类型**：`FetchAdapter.client` 在 `response?.schema` 缺失时落空到
   `t.createParenthesizedExpression(t.createAwaitExpression(...))`（无 cast）。
   真实原因是 **`response?.schema` 在 spec 没声明响应 schema 时就是 `undefined`**——
   不能修复「无 schema」，但可以**默认 cast 成 `unknown`** 让 TS 不再 `any`，
   并把返回值类型标成 `Promise<unknown>`。

2. **数组 body 类型退化**：`Generator.toRequestBodyTypeNode` (`generator/index.ts:273-281`)
   调用 `Generator.toTypeNode` 处理 schema；如果 schema 是 `{ type: 'array', items: ... }`，
   但 schema 顶层没有显式 `type`（只有 `items`），会走到 `default` 分支返回 `unknown`。
   实际上 OpenAPI 3.x 的 `requestBody.content[...].schema` 顶层如果是数组 schema
   （`type: 'array'`），走 `case ArraySchemaType.array` 分支应该是 OK 的——需要
   **重现并写测试** 来确认到底是解析阶段丢了 `type` 还是生成阶段错了。

### 修复策略

1. 响应类型：`response?.schema` 缺失时，返回值标注为 `Promise<unknown>`；在 fetch
   adapter 的「无 cast」分支里也加 `as unknown`（虽然 `unknown` 是无操作，但保证
   一致性）。

2. 数组 body 退化：补一个最小 spec 重现。如是 `V2/V3/V3_1` 解析阶段的问题（顶层
   `type: array` 没传），修对应 provider；如是生成阶段，修 `toRequestBodyTypeNode` /
   `toTypeNode`。

### 验收

- 即使 spec 没声明响应 schema，生成函数也有显式返回值类型（`Promise<unknown>`）。
- spec 声明了 array schema 作为请求 body 时，`req` 的类型是数组元素类型而不是 `unknown`。

## 8. undefined query 拼出字面量 "undefined" (#8)

### 现象

可选 query 参数为 `undefined` 时，URL 里出现 `?key=undefined`。

### 根因

`Generator.toUrlTemplate` (`generator/index.ts:98-144`) 直接用
`encodeURIComponent({name})` 拼接，没过滤 `undefined` / `null`。

### 修复策略

改 `toUrlTemplate`：可选（`required === false`）参数，生成的 template 表达式用
`{name} != null ? '&' + ... : ''`，即：

```ts
// pseudo for optional query params
templateSpan: `${qpName} != null ? \`&${encodeURIComponent(qpName)}=${'${' + camelName + '}'}\` : ''`
```

但要拼成 TS template expression 比较复杂。折中方案：

- 给 query 参数生成一个「可选片段」：`'' + ((value != null) ? '&key=' + encodeURIComponent(String(value)) : '')`。
- 然后把这一段放在主 template 表达式中。
- 或者更简单：**强制 query 参数都 cast 成 `string`**，并在请求前 `URL.searchParams.delete` —— 但会破坏现有 API。

最干净的实现：把 query 部分改为**拼接一个 URLSearchParams**，例如：

```ts
const sp = new URLSearchParams();
if (param0 != null) sp.append('status', String(param0));
if (param1 != null) sp.append('page', String(param1));
const url = `${basePath}${pathSegments.join('')}${sp.toString() ? `?${sp}` : ''}`;
```

放在生成的函数体前，**并保持 `toUrlTemplate` 仍然返回 url 表达式**（path 模板）。
再把 query 字符串接到 url 后。

> 该方案也会解决「同一参数多次出现」与「值为 0 / false / 空串」的边界行为。

### 验收

- 可选 query 参数为 `undefined` 时，URL 不出现 `?key=undefined`。
- 必填 query 参数为 `undefined` 时，原样保留（用户应当传字符串）—— 但仍不输出
  `undefined` 字面量（如果用户传了 `undefined`，应被合理编码或省略）。

## 9. Vite 插件无缓存，每次启动都重跑 (#9)

### 现象

每次 vite env 启动（dev client+ssr、build、typegen）都触发 codegen，
单次 ~3s，dev 体验差。

### 根因

`src/vite-plugin/index.ts:186` 的 `config()` hook 没有短路条件，
env.command 与具体 plugin option 都没用作 cache key。

### 修复策略

1. **基于 spec mtime + 配置 hash 的 cache**：
   - cache key = `hash(option) + hash(spec 绝对路径) + mtime`。
   - cache 落地到 `node_modules/.apicodegen-cache/<hash>.json`，内容是上次生成的
     code + stats。
   - 命中且 spec 文件 mtime 未变且 option 配置未变 → 跳过 `codeGen`，直接复用上次
     code。
   - **type check 仍然每次跑**（tsc 改动是用户的事）—— 或也可缓存，但默认仍跑。

2. **`Promise.all(options.map(generateForOption))`** 保留并发，但每个内部先查 cache。

3. **watch 模式**：cache 失效后增量重新生成（Vite 自身有 HMR）。

> 这是一个比较大的特性，建议做成可选：
> - 在 `ApiCodeGenPluginOptions` 里加 `cache?: boolean` (默认 true)。
> - 在 CLI 不做 cache（CLI 是显式运行，无需缓存）。
> - cache miss 时打印 debug 日志。

### 验收

- 第二次启动 vite（spec 未改）耗时显著下降（接近 0）。
- spec 改动后正常重新生成。
- 加测试：模拟「同 spec 第二次调用」应命中缓存（mock `codeGen` 调用次数为 0）。

## 10. peer vite ^7 与 vite 8 不匹配 (#10)

### 现象

`peerDependencies.vite = ^7`，但 vite 8 已发布；实际代码兼容（只是类型引用），但
install 会警告。

### 修复策略

- 把 peer 改成 `^7 || ^8`，保留 `peerDependenciesMeta.vite.optional = true`。
- 同步 `devDependencies.vite` 不动（保持 7.x dev 构建）。
- README 标注「tested with vite 7 / 8」。

### 验收

- `pnpm install` 在 vite 8 工程下不报 peer 警告。
